## 🎯 디렉토리 구조 개요

### 기본 구조

```
/data/
└── {프로젝트명}/
    ├── runid_00001/
    │   ├── metadata.json           ← runid 메타데이터
    │   ├── Step001/
    │   │   ├── metadata.json       ← Step 메타데이터
    │   │   ├── input.txt           ← KooMeshModifier 입력 (자동 생성)
    │   │   ├── dynain              ← 출력 파일
    │   │   ├── d3plot01            ← 출력 파일
    │   │   └── .lock               ← 완료 표시
    │   ├── Step002/
    │   │   ├── metadata.json
    │   │   ├── input.txt
    │   │   ├── dynain
    │   │   ├── d3plot01
    │   │   └── .lock
    │   └── Step003/
    │       └── ...
    ├── runid_00002/
    │   └── ...
    └── runid_XXXXX/
        └── ...
```

## 📄 metadata.json 형식

### runid 메타데이터 (runid_XXXXX/metadata.json)

```json
{
  "scenario_id": "Fib10K_DOE10_3Steps_S003",
  "doe_index": 1,
  "runid": "runid_00001",
  "created_at": "2026-01-23T10:30:00"
}
```

**목적**:
- runid와 시나리오 연결 정보
- 전체 runid 메타데이터

---

### Step 메타데이터 (runid_XXXXX/StepXXX/metadata.json)

```json
{
  "scenario_id": "Fib10K_DOE10_3Steps_S003",
  "step_number": 1,
  "doe_index": 1,
  "runid": "runid_00001",
  "registered_at": "2026-01-23T10:30:00",
  "angle": {
    "roll": 45.5,
    "pitch": -30.2,
    "yaw": 0.0
  },
  "template": "DROP_FIRST"
}
```

**목적**:
- Step별 해석 조건 (각도, 템플릿)
- Array Job에서 이 정보를 읽어 KooMeshModifier 실행

## 📝 KooMeshModifier 입력 파일 규칙

### input.txt 형식 (자동 생성)

**위치**: `/data/{프로젝트명}/runid_XXXXX/StepXXX/input.txt`

**내용** (Step 1 예시):

```txt
# KooMeshModifier Input Configuration
# Auto-generated by LargeScaleDOEManager

template=DROP_FIRST
roll=45.5
pitch=-30.2
yaw=0.0
step=1

# 결과 경로 (상대 경로)
result_dir=./
```

**내용** (Step 2+ 예시):

```txt
# KooMeshModifier Input Configuration
# Auto-generated by LargeScaleDOEManager

template=DROP_CUMULATIVE
roll=23.7
pitch=-15.3
yaw=0.0
step=2

# 결과 경로 (상대 경로)
result_dir=./

# 이전 Step dynain 경로
prev_dynain=../Step001/dynain
```

## 🔑 핵심 규칙

### 1. 경로는 상대 경로 사용

**이유**:
- `/data` 경로가 클러스터마다 다를 수 있음
- 상대 경로로 작성하면 이식성 향상

**예시**:
```txt
# ✅ 올바른 방법 (상대 경로)
result_dir=./
prev_dynain=../Step001/dynain

# ❌ 잘못된 방법 (절대 경로)
result_dir=/data/Project/runid_00001/Step002
prev_dynain=/data/Project/runid_00001/Step001/dynain
```

---

### 2. 작업 디렉토리 = Step 디렉토리

**Slurm 스크립트에서**:
```bash
cd "$STEP_DIR"  # /data/Project/runid_00001/Step002

/opt/KooMeshModifier/run.sh --input="$INPUT_TXT"
```

**KooMeshModifier는 현재 디렉토리에서 실행**:
- `./` = 현재 Step 디렉토리
- `../Step001/` = 이전 Step 디렉토리

---

### 3. 이전 Step dynain 참조

**Step 1**:
- 이전 dynain 없음
- `prev_dynain` 항목 없음

**Step 2+**:
```txt
prev_dynain=../Step{n-1:03d}/dynain
```

**예시**:
- Step 2: `prev_dynain=../Step001/dynain`
- Step 3: `prev_dynain=../Step002/dynain`
- Step 10: `prev_dynain=../Step009/dynain`

## 🔒 Lock 파일 규칙

### Lock 파일 생성 시점

**Slurm 스크립트에서 KooMeshModifier 실행 성공 후**:

```bash
# KooMeshModifier 실행
/opt/KooMeshModifier/run.sh --input="$INPUT_TXT"

# Exit code 체크
EXIT_CODE=$?
if [ $EXIT_CODE -ne 0 ]; then
    echo "❌ KooMeshModifier 실패"
    exit $EXIT_CODE
fi

# Lock 파일 생성
LOCK_FILE="$STEP_DIR/.lock"
cat > "$LOCK_FILE" << EOF
{
  "completed_at": "$(date -Iseconds)",
  "exit_code": $EXIT_CODE
}
EOF
```

---

### Lock 파일 형식

**위치**: `/data/{프로젝트명}/runid_XXXXX/StepXXX/.lock`

**내용**:
```json
{
  "completed_at": "2026-01-23T12:45:30",
  "exit_code": 0
}
```

---

### Lock 파일 활용

**진행률 확인**:
```bash
# 전체 완료된 Step 수
find /data/Project -name '.lock' | wc -l

# Step 1 완료된 runid 수
find /data/Project/runid_*/Step001 -name '.lock' | wc -l

# Step 2 완료된 runid 수
find /data/Project/runid_*/Step002 -name '.lock' | wc -l
```

**완료 대기**:
```bash
# Step 1 완료 대기 (Python)
python3 Runner/LargeScaleDOEManager.py runner_config.json --wait=1

# Step 1 완료 대기 (Shell)
while true; do
    COMPLETED=$(find /data/Project/runid_*/Step001 -name '.lock' | wc -l)
    TOTAL=$(find /data/Project -maxdepth 1 -name 'runid_*' | wc -l)

    echo "진행률: $COMPLETED / $TOTAL"

    if [ $COMPLETED -eq $TOTAL ]; then
        echo "완료!"
        break
    fi

    sleep 60
done
```

### 소규모 예시 (Cuboid 26 × DOE 5 × 3 Steps = 390 Jobs)

```
/data/Cuboid_Project/
├── runid_00001/
│   ├── metadata.json
│   ├── Step001/
│   │   ├── metadata.json
│   │   ├── input.txt
│   │   ├── dynain
│   │   ├── d3plot01
│   │   └── .lock
│   ├── Step002/
│   │   ├── metadata.json
│   │   ├── input.txt
│   │   ├── dynain
│   │   ├── d3plot01
│   │   └── .lock
│   └── Step003/
│       └── ...
├── runid_00002/
├── ...
└── runid_00130/  (26 각도 × 5 DOE = 130 runid)
```

**총 파일 수**:
- runid: 130개
- Step 디렉토리: 130 × 3 = 390개
- metadata.json: 130 (runid) + 390 (Step) = 520개
- Lock 파일: 390개 (완료 시)
- 출력 파일: 390 × 2 (dynain, d3plot01) = 780개

### 대규모 예시 (Fibonacci 10,000 × DOE 10 × 3 Steps = 300,000 Jobs)

```
/data/Fib10K_Project/
├── runid_00001/
│   ├── metadata.json
│   ├── Step001/
│   ├── Step002/
│   └── Step003/
├── runid_00002/
├── ...
└── runid_100000/  (10,000 각도 × 10 DOE = 100,000 runid)
```

**총 파일 수**:
- runid: 100,000개
- Step 디렉토리: 100,000 × 3 = 300,000개
- metadata.json: 100,000 + 300,000 = 400,000개
- Lock 파일: 300,000개 (완료 시)
- 출력 파일: 300,000 × 2 = 600,000개

**디스크 용량 예상**:
- metadata.json: ~1 KB/파일 × 400,000 = ~400 MB
- Lock 파일: ~0.5 KB/파일 × 300,000 = ~150 MB
- 출력 파일 (dynain, d3plot01): ~100 MB/runid × 100,000 = ~10 TB

### 3. Lock 파일 체크 성능

**대규모시 find 명령이 느릴 수 있음**:

**해결책**:
```bash
# 카운터 파일 사용
/data/Project/.counter_step001  ← 완료 개수만 저장

# Lock 생성 시 카운터 증가 (atomic)
flock /data/Project/.counter_step001 \
  bash -c 'echo $(($(cat /data/Project/.counter_step001 2>/dev/null || echo 0) + 1)) > /data/Project/.counter_step001'
```
