# 컨텍스트 노트 — ten nodes format 절삭 절점줄

## 2026-10-22
- 접수된 진단은 다른 세션이 쓴 것으로 보인다. 결론(64자 줄을 완결 카드로 봐야 한다)은 맞지만 메커니즘은 달랐다.
  - 진단은 "짧은 줄을 조용히 버린다" 고 했다.
  - 실제로는 다음 요소의 헤더를 n9·n10 으로 먹고, 그 요소의 노드줄을 "헤더 형식 이상"으로 버린다. 경고는 한 번 찍힌다.
  - 개수 검사는 파싱 결과끼리 비교해서 "소실 0" 이 나온다.
- "I8 은 한 줄 = 카드" 로 바꾸는 단순한 수정은 쓰지 않는다. 7월에 넣은 넘김 처리(8+2·4+4+2·2개씩·1개씩)를 실제 덱 근거 없이 지우게 되기 때문이다.
  - 그 근거는 B7 의 I10 8+2 추정과 적대 리뷰 F3(2개씩 TET10)였다. 매뉴얼에는 넘김이 없지만 7월 판단을 뒤집을 실덱이 이 서버에 없다.
  - 그래서 "지금 요소를 잃는 경우만" 바꾼다. 그래야 오늘 정상인 덱의 출력이 바뀌지 않는다는 회귀 증명이 선다.
- 판정 신호는 "8개 받은 뒤 2필드 줄, 그다음 줄이 2필드가 아님" 이다. 처음엔 '3필드 이상' 이었다가 아래 무작위 차분에서 넓혔다.
  - 진짜 n9·n10 줄 뒤에는 다음 헤더(2필드)나 블록 끝만 온다. 노드줄이 올 수 없다.
  - 2개씩 넘김 TET10 은 2필드 줄 뒤에 또 2필드 줄이 오므로 이 규칙에 걸리지 않는다.
- 이 서버의 Examples·/data 에서 `ten nodes format` 실덱은 찾지 못했다(A27·B7 은 현장 덱). 그래서 회귀 근거는 합성 매트릭스와 옛/새 함수 차분이다.
- 무작위 차분에서 241블록이 더 틀렸다. 모두 '절삭 뒤 1개씩 넘김' 이었다.
  - 다음 줄이 1필드인 경우를 처음 규칙(다음 줄 3필드 이상)이 놓쳤다.
  - 진짜 n9·n10 뒤에는 1필드 줄이 올 수 없다(요소가 완결돼 다음은 헤더여야 한다). 그래서 규칙을 '다음 줄이 2필드가 아니면' 으로 넓혔다.
  - 옛 판도 이 경우 그 1필드 줄을 '헤더 형식 이상' 으로 버렸다. 그래서 '옛 판이 줄을 버린 경우만 바뀐다' 는 성질은 유지된다.
- 남은 한계는 '절삭 뒤 2개씩 넘김' 이다. 2필드 줄 다음도 2필드라 모양만으론 못 가린다. 옛 동작을 그대로 두고 시험에 limit 으로 적었다.
- 빌드(build_without_automatedmodeller.sh)는 Nuitka --jobs=8 이 고정이다. taskset 으로 CPU 를 묶어도 gcc 8개가 동시에 메모리에 올라간다. 헤드 가용 메모리가 9GB 안팎(cpptools 42GB)이면 위험하므로 빌드 전에 메모리를 확보한다.

## 2026-10-23 — 기존 결함 ①② 수정과 리뷰 C
- 사용자가 기존 결함 ①② 도 고치라고 했다("그래 고칠것들도 고쳐야지"). ③ 은 R16 에서 2카드가 표준이라 그대로 둔다.
- ① KooPart mode2 오면체 분기에 `_add_total += 1` 한 줄을 넣었다. CRLF 파일이라 바이트로 치환했다.
- ② ReadKeywordsfromFile 파일 끝 처리.
  - 처음 수정은 '마지막 블록이 END 가 아니면 저장' 이었다. 리뷰 C 가 확정 결함 둘을 찾았다.
    - *END 뒤에 놓인 마지막 블록을 새로 읽었다. *NODE 면 절점 1 이 (5,5,5) 로 옮겨졌고, *INCLUDE parked.k 면 파트가 늘었다. 옛 판은 이 블록을 버렸다.
    - *END 없는 파일이 '*INCLUDE / sub.k / 빈 줄' 로 끝나면 빈 이름이 './' 폴더로 열려 IsADirectoryError(rc 1)로 죽었다. 옛 판은 sub.k 를 조용히 안 읽었다(rc 0).
  - 그래서 규칙을 바꿨다.
    - *END 가 있던 파일은 파일 끝 처리를 하지 않는다. 그래서 옛 판과 바이트가 같다. *END 뒤의 (마지막이 아닌) 블록을 읽는 옛 동작도 손대지 않았다.
    - *END 없는 파일만 끝에 *END 가 있는 것처럼 마감한다. 데이터 없는 마지막 키워드도 루프 안처럼 'Empty keyword found' 로 알리고 목록에서 뺀다. 옛 판·직전 판 모두 여기서 KeyError 였다.
    - *INCLUDE 블록의 빈 줄은 파일 이름으로 보지 않는다. 옛 판에서 이 줄은 늘 크래시(폴더 열기)나 'not found' 경고였다. 그러니 바뀌는 덱은 옛 판이 죽던 덱뿐이다.
- 검증
  - 시험 [3] 을 바꿨다. 리뷰 C 말대로 옛 [3](*END 뒤 잡문)은 가드를 빼도 통과해 아무것도 고정하지 못했다. 이제 '*END 뒤 꼬리(잡문·*NODE·*INCLUDE)가 있어도 출력이 *END 로 끝난 덱과 바이트 같다' 를 본다. [1] 에는 빈 줄 인클루드와 빈 마지막 키워드를 넣었다.
  - 세 판에 돌렸다. 옛 판(HEAD)은 [1]·[2] 8건 FAIL, [3] 통과였다. 직전 판은 리뷰가 짚은 4건만 FAIL 이었고, 새 판은 전부 통과했다.
  - 리뷰 C 말뭉치 84덱을 새 판으로 다시 돌렸다. 모든 파일에 *END 가 있는 덱은 옛 판과 같다(예외는 옛 판이 죽던 빈 줄 인클루드 1건). *END 없는 덱은 *END 를 붙인 ref 와 같다.
  - MinimumModel(솔리드 43,657) 의 model_trans.k·model_dump.k md5 가 옛 바이너리와 같다.
- 남긴 것(기존 결함, 회귀 아님)
  - *ELEMENT_SOLID 블록 안의 빈 줄·Ctrl-Z 줄은 KooPart:2476 에서 ValueError 로 죽는다. *END 가 있어도 같다. *END 없는 파일이 빈 줄로 끝나면 옛 KeyError 대신 이 ValueError 가 난다. 둘 다 크래시라 조용한 손실은 없다.
  - 자기 자신을 인클루드하는 덱은 RecursionError 다(순환 감지 없음). *END 가 있으면 옛 판도 같았다.
  - *END 가 마지막 데이터 줄에 붙은 파일('0.25*END')은 이제 읽힌다. 그 예(옛 KooRemapper 산출물)는 MID 칸이 15자로 밀려 있어 LS-DYNA 도 같은 값(RO=1.0·E=2.0·PR=12000)으로 읽는다. 입력이 틀린 경우다.
  - 데이터 없는 *CONTROL_MPP_IO_NOD3DUMP 류가 출력에서 빠지는 것은 *END 유무와 상관없는 옛 동작이다.
